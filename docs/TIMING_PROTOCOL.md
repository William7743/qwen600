# 请求计时与测量开销（protocol 4）

使用 C++ `std::chrono::steady_clock` 测量 CPU 可见的请求延迟。模型实现与权重没有因本次计时调整而变化。

## 计时区间

- 开始：输入 IDs 就绪、GPU 同步完成之后。
- Prefill 结束：最后输入位置的 logits 阻塞回传 CPU 后。
- TTFT 结束：CPU 完成 greedy argmax，首 token ID 就绪。
- 请求结束：最后输出 token ID 就绪。错误检查和兜底同步仍执行，但放到这个时间点之后；报错的运行仍作废。
- Decode = 请求结束 − 首 token 就绪；TPOT = Decode / (G−1)。正常打点模式下，所有 ITL 之和等于 Decode。

这一边界依赖当前 forward 的阻塞式回传。未来异步实现必须保证返回时 host logits 可读，不能提前返回来缩短计时。
GPU 计算、必要数据传输、CPU token 选择都属于真实推理开销，继续计入。

## 减少辅助操作

全部请求的记录空间在整轮执行前分配并初始化。计时内只保留推理、生成 ID 保存和必要时钟读取；
不进行统计、格式化、打印或写文件。结果在整轮 GPU 请求完成后输出，Python 此前等待，不与后续请求并行解析结果。
因此，运行期间不再逐请求实时打印进度；若中途异常终止，未输出的测量不会形成有效结果。

正式延迟运行不启用显存轮询。显存用相同负载另跑 `--memory-only`，元数据标为 `memory_only`，
其中时间只作诊断，不能充当正式延迟成绩。Nsys、NCU、sanitizer 也不与正式计时同跑。

## 独立校准 ITL 打点

`check_timing_overhead.py` 对同一个二进制交错执行 A=no-itl、B=full，顺序 ABBA+BAAB。
两种模式使用相同预分配缓冲区、模型、输入、输出数量、预热和推理路径；只切换中间 token 的时间戳读取/保存，
通过模板在计时之前选择，生成循环中不判断运行时计时模式。两个模式均保留开始、Prefill、首 token、最后 token 四个边界时间戳。

使用既有固定六条 ShareGPT，每进程先以 s038 预热一次，每条正式测三次。
八个独立进程共 144 次请求，每种模式每条 12 次。保留逐次时间、生成 IDs、二进制与源码哈希和 GPU 前后状态。
检查所有生成 IDs 相同；若提供可信旧记录，还核对其生成 IDs。

主比较：六条请求各自 total_ms 中位数的均值。同时展示四个相邻 A/B 进程对的变化和同模式进程均值的波动范围。
预先规定：仅四对均增加且最小增加量超过两个模式各自进程均值相对极差时，标记可分辨增加；否则标记本次重复次数下无法稳定分辨。
这不是统计显著性检验或误差上界。不会从正式成绩里减去该差值，也不会把负差值解释为“打点加速推理”。
共同保留的四个边界时钟、循环及 ID 保存开销不能由这组开关对照单独识别。它测的是增加 ITL 内部打点路径的影响，不能证明全部工具开销为零。

## 版本

当前使用 protocol 4，默认开启 ITL、关闭显存轮询。比较性能必须使用相同计时协议、负载、模式和预热设置。
历史校准记录保留在 `main` 分支；学生应以自己平台上原始 V0 与候选的测量作为性能对照。
